# Preparing the final research release

`scripts/package_release.py` collects acquired source data, canonical CPS data,
analysis code, publication tables, empirical output, manuscript, and appendix
into a portable release with a SHA-256 inventory. It does not acquire missing
data or treat software tests as evidence about the ADA.

The command checks acquisition provenance, source-variable verification,
empirical execution, independent numerical comparisons, and final rendering.
A documented discrepancy from a historical table is a research finding that
can be packaged honestly. An unrun comparison or failed analysis fit is not
converted into a successful result. These are evidence checks, not external
approval requirements.

## Acquisition and source verification

The current source is the repository author's supplied **GitHub release
archive**, identified by `source_type = "github_release_mirror"`. It contains
the SAS data and paper, without the original SAS analysis programs. The
historical Dataverse DOI remains a referenced source identifier; the mirror
has not been established as a complete acquisition of that deposit. The
packager checks matching source type, release URL, and referenced DOI in
`data/raw/manifest.json` and `data/raw/catalog.json`. The inventory preserves
the declared acquisition scope and DOI qualification.

Every acquired file must be present. File sizes, local SHA-256 hashes, and
recorded checksums are verified again; the checksum's recorded origin must
not be confused with an independently published Dataverse checksum. Supplied
archives are included in full, while extraction copies are omitted to avoid
duplicating large files. `data/derived/cps.rds` is included separately. The
analysis input must link to an acquired file or an extraction carrying its
archive's checksum marker.

`data/source-verification.json` records the publication and source-label audit,
bound to the exact input path and hashes (`input_md5`, `input_sha256`) and
acquisition manifest (`raw_manifest_sha256`). Its `mapping_status` must be
`publication_and_source_labels_verified` and `data_kind` must be `empirical`.
The record must describe the source-label, publication-timing, and weight
evidence in `verification_basis`. Both the acquisition manifest and verification
record must disclose `original_programs_available: false`, and the audit's
limitations must explain that the original programs are absent. This supports
a documented reconstruction, not a claim of original-code equivalence.

Do not create this record merely to satisfy the packager: it summarizes
checks against the actual paper, source labels, sample counts, and data.
Source usage terms should be recorded from the supplied material; the project's
own code license does not automatically license third-party data.

## Executed results and comparison status

The executed run and canonical-data metadata must agree on their input checksum,
source file, run timestamp, commit, and analysis code hashes. Current R source
hashes must still match. Both metadata records must report zero extension
failures. Their matching `replication_status` must accurately describe a
nonempty `results/replication_benchmarks.csv`. Source-variable mapping is a
separate verification question. The comparison table uses these fields:

| Column | Meaning |
| --- | --- |
| `benchmark_id` | Optional unique label identifying the original table/cell; if supplied, it must be nonempty and unique |
| `original_value` | Value transcribed or obtained from the original source, not this project's previous output |
| `reproduced_value` | Value generated by the current reconstruction |
| `tolerance` | Prespecified nonnegative absolute tolerance, consistent with published precision |
| `passed` | `TRUE` exactly when the absolute discrepancy is within tolerance, otherwise `FALSE` |

The existing numeric `target` column is retained by the reconstruction module;
it is not treated as a text identifier. The packager reads the unambiguous
numeric aliases `original_value` and `reproduced_value` and recomputes every
comparison. Missing/NA, infinite, or nonnumeric values, negative tolerances,
and incorrectly recorded pass flags prevent packaging.

Two completed comparison outcomes are supported:

- **`benchmarks_verified`:** every declared comparison meets its tolerance.
- **`reconstruction_discrepancies_reported`:** at least one finite, executed
  comparison exceeds its tolerance, and `docs/replication-audit.md` is present
  to explain the differences. The audit is included in the package.

Metadata status must agree with the recomputed discrepancy count. Optional
metadata counts `replication_benchmarks_total` and `replication_benchmarks_failed`
are checked if supplied. The release inventory records total, passed,
discrepant, and unrun counts, identifies discrepant benchmark IDs, and includes
an explicit note when the package contains discrepancies. A truthful comparison
with unresolved numerical differences is permitted; it is not relabeled as a
perfect replication. Passing all declared benchmarks likewise does not prove
that every historical result was replicated or that identification is valid.

Required outputs include the primary estimates, placebo and distributional
extensions, richer-covariate comparison, overlap/balance diagnostics, sensitivity
results, exported tables, and complete bootstrap records. Prespecified method
and subgroup combinations must be present without duplicates: 32 placebo
estimates, 80 distributional estimates, 64 richer-covariate estimates,
44 corresponding diagnostic rows, and 32 main-window bootstrap summaries.
Each bootstrap summary needs at least 199 successful replications, all requested
replications successful, finite ordered intervals, and matching saved
replicate/status records. A nonempty extension failure table still blocks the
release. These checks establish computational completeness; they do not turn
the individual bootstrap into CPS survey-design or national-policy uncertainty.

Both HTML and PDF versions of `report/paper.qmd` and `report/appendix.qmd` must be
rendered after the current results and report source. Modification times catch
obviously stale documents, while the release hashes inventory exactly what was
packaged. Neither check independently proves that a manuscript's prose correctly
interprets its inputs.

## Commands and output

After source verification, completed benchmark comparisons, and empirical
execution, render the final documents and create the bundle:

```bash
quarto render report/paper.qmd --to html
quarto render report/paper.qmd --to pdf
quarto render report/appendix.qmd --to html
quarto render report/appendix.qmd --to pdf
python3 scripts/package_release.py
```

The default destination is `release/`. Manuscript files are placed in
`release/manuscript/`, appendix files in `release/appendix/`, and source/data/result
files retain their repository-relative organization. `release/manifest.json`
records original relative paths, release paths, sizes, SHA-256, artifact
categories, and large-file status. Its `source` object records the actual
GitHub acquisition and limitations, and `replication_comparison` records
numerical status and discrepancy counts. Runtime environments, caches, and
`results/run-*` scratch directories are excluded. Extracted data are recoverable
from the included supplied archives.

For a space-efficient check that writes only the inventory:

```bash
python3 scripts/package_release.py --manifest-only --output release-inventory
```

`materialized: false` marks an inventory-only output; it is not a complete bundle.
The command refuses to replace an existing destination. Inspect and preserve an
existing release, or choose another `--output` directory. No Git commit or push
is performed.

Files larger than 95 MiB remain in the bundle and are explicitly listed as needing
Git LFS before committing/pushing to GitHub. The script never silently drops them
or replaces actual data with an empty pointer. The threshold is conservative
relative to GitHub's regular-file limit. Git LFS setup and GitHub publication are
separate from building and checking the local release.

Tests construct labeled software fixtures in temporary directories and inject
fixture metadata readers. They cover an honestly discrepant package, incorrect
pass flags, unavailable comparisons, inconsistent provenance, and the unchanged
analysis-completeness requirements. There is no command-line option to bypass
empirical provenance checks or manufacture a synthetic research release.
